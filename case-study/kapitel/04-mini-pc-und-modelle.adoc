== Der Mini-PC und seine Modelle

_Teilfrage T3. Reicht ein Mini-PC für den Betrieb und welche Modelle passen?_

.Auf einen Blick
====
*Worum es geht.* Der Mini-PC, seine Schichten von der Hardware bis zur Anwendung und die Messungen, nach denen wir Engines und Modelle gewählt haben.

*Ergebnis.*

* Ein Mini-PC mit 64 GB gemeinsamem Speicher hält Sprachmodell, Decision-Modell und Embedding-Modell gleichzeitig geladen.
* Ein Reparaturansatz ist in knapp 30 Sekunden fertig, eine Einordnung in Sekundenbruchteilen.
* Im Echtbetrieb laufen auf dem Mini-PC nur die Modelle und Open WebUI, Zammad und n8n laufen auf der Helpdesk-VM. Vorher läuft eine Testumgebung auf MANUEL <<adr-0043>>.
* Das Sprachmodell läuft mit llama.cpp, `d3:9b` und `bge-m3` mit Ollama <<adr-0025>>.

*Wichtigste Befehle.*

[source,bash]
----
sudo podman run -d --name ollama --restart=always --device /dev/dri \
  -e OLLAMA_IGPU_ENABLE=1 -v ollama:/root/.ollama -p "$(tailscale ip -4):11434:11434" \
  docker.io/ollama/ollama:latest
ollama run qwen3.6:35b-a3b "Mein Wasserkocher schaltet sich nicht mehr ein."
./bench.sh lang-qwen36-mtp llamacpp-vulkan
----

=== Überblick

* Diagramm aus dem PLAN, Mini-PC im Makerspace hinter NAT, Helpdesk-VM im Rechenzentrum
* Verbindung über NetBird, im Makerspace werden keine Ports geöffnet <<adr-0020>>. Bis NetBird läuft, verbindet Tailscale, und alle Dienste von MANUEL hören nur auf seiner Adresse im Tailnet <<adr-0042>>, <<adr-0047>>.
* Zammad nutzt KI-Agenten und füllt die Felder selbst <<adr-0018>>, die Wissensdatenbank sammelt Anleitungen <<adr-0022>>
* n8n übernimmt nur, was außerhalb von Zammad liegt <<adr-0019>>
* Open WebUI für Tests und später den Chat. Bis NetBird läuft, steht es im Tailnet ohne Anmeldung bereit, und Engagierte können Ollama auch mit eigenen Werkzeugen wie opencode ansprechen <<adr-0047>>. Später kommt die Anmeldung über authentik.

[[schichten]]
=== Die Schichten von MANUEL

* MANUEL besteht aus Schichten, die aufeinander aufbauen. Jede lässt sich für sich austauschen, etwa die Engine, ohne das Modell zu wechseln.

[cols="2,4,5",options="header"]
|===
|Schicht |Aufgabe |Beispiel bei MANUEL
|Hardware |rechnet |Mini-PC mit Radeon 890M und 64 GB gemeinsamem Speicher
|Betriebssystem |startet und aktualisiert alles |eigenes Image auf Basis von uCore <<adr-0016>>
|Inferenz |führt ein Modell aus |Ollama und llama.cpp im Container <<adr-0025>>
|Modell |liest und schreibt Text, wählt Werte, vergleicht Bedeutung |`qwen3.6:35b-a3b`, `d3:9b`, `bge-m3`
|Harness |gibt dem Modell Auftrag, Kontext und Werkzeuge und prüft die Antwort |Ticket Categorizer von Zammad, Skripte in `eval/`, n8n, Hermes, Claude Code
|Anwendung |dort arbeiten Menschen |Zammad, Open WebUI
|===

* Der Irrweg mit Hermes zeigt, dass die Schicht Harness entscheidet, wie gut ein Modell arbeitet. Dasselbe Modell lieferte mit festen Skripten nachvollziehbare Ergebnisse, als Agent mit viel Freiheit nicht.

[[hardware]]
=== Mini-PC und Betriebssystem

* MINISFORUM AI X1 Pro-370 mit AMD Ryzen AI 9 HX 370, Radeon 890M, 64 GB DDR5 und 1 TB SSD
* Eigenes Image auf Basis von uCore, täglich neu gebaut, Wechsel per `bootc switch` <<adr-0016>>
* Inbetriebnahme nach {repo}/docs/inbetriebnahme.md[docs/inbetriebnahme.md]

=== Messmethodik

* `ollama-bench` und `llama-bench`, Prompts mit 512 und 4096 Tokens, mehrere Läufe
* Was nicht gemessen wurde, etwa die Qualität der Antworten, die erst der Testsatz zeigt

=== So laufen die Modelle

* Ollama läuft im Container und hört nur auf der Adresse von Tailscale <<adr-0047>>. `OLLAMA_IGPU_ENABLE=1` ist nötig, sonst rechnet Ollama auf der CPU.

[source,bash]
----
sudo podman run -d --name ollama --restart=always \
  --device /dev/dri --cap-add PERFMON --security-opt label=disable \
  -e OLLAMA_IGPU_ENABLE=1 -e OLLAMA_CONTEXT_LENGTH=32768 \
  -v ollama:/root/.ollama -p "$(tailscale ip -4):11434:11434" \
  docker.io/ollama/ollama:latest
----

* Im Terminal von MANUEL funktioniert `ollama` wie auf dem Host, das Image leitet den Befehl in den Container. Modelle von Hugging Face lassen sich direkt laden.

[source,bash]
----
ollama run qwen3.6:35b-a3b "Mein Wasserkocher schaltet sich nicht mehr ein. Was prüfe ich zuerst?"
ollama run hf.co/<benutzer>/<repo>:<quantisierung>
----

* llama.cpp lief im Benchmark so, mit der Datei des Modells aus Ollama und MTP.

[source,bash]
----
sudo podman run -d --name llamacpp-vulkan --security-opt label=disable \
  --device /dev/dri -v <ordner-mit-gguf>:/models:ro -p 127.0.0.1:8080:8080 \
  ghcr.io/ggml-org/llama.cpp:server-vulkan \
  -m /models/<datei> -ngl 99 -c 32768 --parallel 1 --host 0.0.0.0 --port 8080 \
  -ub 1024 --spec-type draft-mtp --spec-draft-n-max 2 --spec-draft-backend-sampling
----

=== Engines im Vergleich

* llama.cpp mit Vulkan, `-ub 1024` und MTP ist bei fast allen Modellen etwas schneller.
* `d3:9b` läuft nur über die Decision-Funktion von Ollama, deshalb laufen beide Engines nebeneinander <<adr-0025>>.

=== Modelle im Vergleich

* `qwen3.6:35b-a3b` ist als Mixture-of-Experts-Modell mit rund 3B aktiven Parametern je Token unter den größeren Modellen am schnellsten <<adr-0023>>.
* Es versteht Deutsch und Bilder, etwa Fotos von Typenschildern.
* Für schwierige Fälle käme `qwen3.8:27b` mit rund 100 Sekunden für eine lange Antwort in Frage.

=== Speicher

* 16 GiB UMA geben der GPU 39,3 statt 32,2 GiB, alle drei Modelle passen zusammen auf die GPU <<adr-0024>>.
* Nach einem Wechsel des Modells dauert die erste Antwort 26 statt 0,27 Sekunden.

=== Decision-Modelle

* `d3:9b` trennt an erfundenen Tickets sicherheitsrelevante Fälle fast perfekt <<adr-0003>>.
* Das Ergebnis ist immer ein gültiger Wert, und die Sicherheit lässt sich über eine Schwelle einstellen.
* Als Embedding-Modell dient `bge-m3`, mehrsprachig und von Zammad unterstützt <<adr-0021>>. Es unterstützt über 100 Sprachen cite:[chen-2024].
