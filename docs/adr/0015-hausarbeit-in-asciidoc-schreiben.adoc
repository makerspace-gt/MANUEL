== Kontext und Problem

MANUEL wird am Ende ausführlich dokumentiert, wie die Datenpotenzialanalyse von 2022 als Hausarbeit. Seit xref:0030-rahmen-der-fallstudie-festlegen.adoc[ADR 30] heißt die Arbeit Fallstudie. Es gibt keine Vorgaben und keine Bewertung. Die Arbeit soll vor allem online gelesen werden, sich aber auch gut als PDF drucken lassen. Tabellen, Skripte und Ergebnisse sollen direkt aus dem Repo zitiert werden, damit Arbeit und Daten nicht auseinanderlaufen.

== Entscheidungskriterien

* Dateien aus dem Repo direkt einbinden
* Online lesbar und als PDF druckbar
* Literaturverzeichnis

== Betrachtete Optionen

* AsciiDoc mit Asciidoctor
* Typst
* Markdown
* ODT wie die Datenpotenzialanalyse

== Entscheidung

Die Fallstudie entsteht in AsciiDoc. Sie bindet Tabellen und Codeausschnitte mit `include` direkt ein. Eine GitHub Action erzeugt daraus eine HTML-Seite für GitHub Pages und mit asciidoctor-pdf ein PDF. Die Daten werden bei Abschluss mit einem Git-Tag eingefroren, damit Zitate auf genau diesen Stand verweisen. Das Literaturverzeichnis setzt asciidoctor-bibtex aus `literatur.bib`, siehe xref:0031-literatur-mit-zotero-und-bibtex-verwalten.adoc[ADR 31] und xref:0037-zitierstil-chicago-nach-autor-und-jahr-nutzen.adoc[ADR 37].

=== Konsequenzen

* Gut, weil Tabellen und Code nicht von Hand abgeschrieben werden.
* Gut, weil auch die ADRs in AsciiDoc vorliegen und als Anhang eingebunden werden.
* Schlecht, weil GitHub beim Anzeigen von AsciiDoc keine eingebundenen Dateien zeigt. Gelesen wird die Arbeit deshalb über GitHub Pages.

== Vor- und Nachteile der Optionen

=== AsciiDoc mit Asciidoctor

* Gut, weil es Dateien aus dem Repo einbindet und HTML und PDF aus derselben Quelle erzeugt.
* Schlecht, weil GitHub eingebundene Dateien nicht anzeigt.

=== Typst

* Gut, weil es CSV und Literatur im Format CSL von Haus aus kann.
* Schlecht, weil GitHub Typst nicht anzeigt.

=== Markdown

* Gut, weil es fast alle kennen und GitHub es direkt anzeigt.
* Schlecht, weil Markdown keine Dateien einbinden kann.

=== ODT wie die Datenpotenzialanalyse

* Gut, weil es sich mit LibreOffice ohne Vorkenntnisse bearbeiten lässt.
* Schlecht, weil Tabellen und Ergebnisse von Hand übertragen werden und Änderungen in Git schwer zu verfolgen sind.
